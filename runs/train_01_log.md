# 第一次训练的性能排查

## 现象与原因

排查时，原训练已完成第 39 轮，第 40 轮正在运行。第 38、39 轮分别用时 73.7 秒、74.1 秒，均含 68 个训练月和 24 个验证月。容器的 CPU 配额相当于 12 核，原训练进程约占 97.7% 的单核容量，主线程约占 95.9%。GPU 连续 8 个每秒采样为 0% 或 5%，显存约 795 MiB。这组采样覆盖训练的一小段。

原代码像是让一名员工独自备料。每一步先由主线程打开当月及前两个月相关的 NetCDF 文件，解压、标准化、做掩膜和剖面背景插值，再把数组交给 GPU。GPU 算完一个月的数据后，下个月才开始备料。设置 `--cpu-threads 12` 主要控制 PyTorch 的 CPU 运算线程数，不会自动把 NetCDF 读取和 NumPy 数据准备分给 12 个核心。

每个训练步还有多次把 GPU 损失转成 Python 数字的操作，验证也逐月转出多种指标。CPU 取数时要等待 GPU 执行到相应位置。模型每步只有一个月，显存使用少，GPU 利用率仍需要结合每轮耗时判断。

## 处理和验证

- 新入口在 `/workspace/srtp-ocean/code/parallel_training/run_parallel.sh`。默认用 4 个训练加载进程和 2 个验证加载进程，按原顺序交付样本。GPU 计算当前月时，CPU 可准备后续月份。
- CUDA 下使用页锁定内存和非阻塞传输。损失与验证统计在 GPU 上累计，记录日志或整轮结束时再取回。开启 `--cache-gib 8` 后，已放入显存的月份在后续轮次直接复用，可减少重复的 NetCDF 读取和数据准备。
- 多进程会让原先闲着的部分 CPU 核开始工作，加载阶段的 CPU 总利用率可能上升。减少后续轮次的 CPU 工时主要靠复用已准备好的数据。
- 真实数据 CPU 对照采用 2 个训练月、2 个验证月、2 轮和相同随机种子。原版和并行版的训练损失、验证指标及有效点评估计数逐项一致。
- 同样 12 个训练月仅测数据准备。进程启动后的第二遍，串行 9.25 秒，4 进程 2.80 秒，约 3.3 倍。包含进程启动的第一遍分别为 9.47 秒和 11.95 秒。
- 原作业结束后，已在同一张 A800 上用并行版从头完成 50 轮，实测见下节。

[PyTorch 性能调优指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)

## A800 实测

并行版采用 6 个训练加载进程、2 个验证加载进程和 8 GiB 缓存上限。训练与验证月份、模型参数、随机种子和 AMP 设置与原版一致。首轮 42.14 秒，缓存覆盖全部 92 个月，实占 5.772 GiB。第 2–50 轮的 NetCDF 读取计数均为 0，单轮中位耗时由原版 74.26 秒降到 1.91 秒。

50 轮训练与验证的逐轮耗时合计由 3,785.1 秒降到 143.5 秒，约 26.4 倍加速。这一结果来自并行加载、显存缓存和减少同步的合计效果。两版最佳都在第 49 轮，验证分数分别为 1.9210595 和 1.9210806。详细输出位于 `/workspace/srtp-ocean/runs/swin_physics_parallel_6w_v1/`。
